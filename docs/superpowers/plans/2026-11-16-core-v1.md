# Core v1 Implementation Plan (spike, shared total-time budget, one kid, two PCs)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A kid's weekly total time is set and adjusted from an HA dashboard, shared across several PCs, enforced by timekpr-next on each PC, with daily statistics recorded from day one.

**Architecture:** `tk-agent` (per PC, root) measures and enforces through the `timekpra` CLI and talks MQTT. `tk-budget` (HA add-on) sums usage per kid and week, publishes `remaining`, owns settings, adjustments, statistics and the HA discovery entities. Both use one small shared `tk_protocol` package (topics, payloads, bus abstraction).

**Tech Stack:** Python 3.11+, pytest, paho-mqtt ≥ 2.0 (`CallbackAPIVersion.VERSION2`), sqlite3 (stdlib), Mosquitto, HA add-on (Docker), Arch `PKGBUILD` + systemd.

**Spec:** `docs/superpowers/specs/2026-11-16-timekpr-ha-design.md`

**Scope:** This plan covers spec build steps 0–2 (spike, v1 for one kid, second client). Play time (weekly play budget, daily play cap, today's adjustment), play-lock actions, the Family Link adapter and statistics views get their own plans after the spike results are in, because they depend on what `timekpra` and the integration actually do.

## Global Constraints

- timekpr is touched only through the `timekpra` CLI; never import timekpr Python modules.
- `tk-agent` runtime dependencies: Python stdlib + `python-paho-mqtt` from pacman. No pip on clients.
- Week = ISO week, Monday start, key format `%G-W%V` (e.g. `2026-W47`); day key `YYYY-MM-DD` in the PC's/HA's local time.
- Usage is reported **cumulative** per week and per day (idempotent, resend-safe). Never report deltas.
- Fail closed: without a fresh `remaining`, the agent keeps enforcing the last known one; it never grants unlimited time.
- Report/poll interval default 45 s (allowed 30–60 s).
- Agent config `/etc/tk-agent.conf` mode 600 root:root; one Mosquitto user per client.
- Adjustments reset at the week change; nothing carries over.
- Commit messages must not contain `Claude-Session` lines.

## Review Focus

Failure modes the spec implies but no task would exercise by default; each has a named test in the owning task.

1. Agent restart or crash between writing time-left and the next poll: no usage lost, none counted twice (Task 6).
2. Broker outage, then reconnect with stale retained or resent cumulative values: totals never decrease or double (Task 3).
3. Week and day boundaries (Sunday 23:59 → Monday 00:00, midnight rollover of timekpr's daily counter) (Tasks 3, 6).
4. Remaining at or below zero, negative adjustments larger than the budget, budget lowered below usage: clamp at 0, no crash (Task 3).
5. A PC that was off for days comes back reporting an old week; or a malformed/unknown-kid payload arrives: ignored, never corrupts totals (Tasks 3, 5).
